# ТЗ №2 для агента репозитория BMGBRAND — «больше воли» AI-агенту

> Документ подготовлен агентом приложения **AdminBMG** для агента, работающего с репозиторием
> сайта `https://github.com/misha4323223/BMGBRAND`. Все изменения — ТОЛЬКО на сервере сайта.
> Предыдущее ТЗ (`docs/tz-site-agent.md` в репо AdminBMG) выполнено — спасибо, рефакторинг
> в `server/admin-tools.ts` отличный, на нём и строимся.

## Контекст: зачем

Администратор управляет магазином через чат с агентом в приложении AdminBMG. Сейчас агент
ограничен жёстко, и это видно на живых примерах:

- «покажи брошенные корзины **за вчерашний день**» → инструмент не имеет параметров даты,
  запрос молча игнорируется, показывается общий топ-20 (с корзинами 180+ дней давности);
- нельзя задать конкретный период («выручка с 1 по 15 августа») — только относительный `days`;
- агент **не может соединять данные**: «найди товар → посмотри кто его покупал → посчитай сумму»
  требует цепочки инструментов, а модель отвечает ровно одним действием за сообщение;
- результаты read-инструментов Groq не видит → не может сделать выводы, сравнить, пересказать.

Цель: агент должен понимать **любую** формулировку админа и при необходимости выполнять
несколько шагов сам. Ниже 5 задач по приоритету.

---

## Задача 1 (главная): серверный цикл инструментов вместо одного действия

Сейчас: клиент шлёт `POST /api/admin/agent/chat`, модель возвращает один JSON
(`read`/`write`/`answer`), read-инструмент выполняет КЛИЕНТ, результат показывается админу,
но модели обратно не попадает.

**Файлы:** `server/admin-agent.ts` (+ возможно новый `server/admin-agent-loop.ts`).

Переделать `processAdminCommand` в цикл на сервере:

```
1. Вызвать Groq с SYSTEM_PROMPT + история.
2. Если ответ = {"type":"read", tool, params}:
   - выполнить инструмент НА СЕРВЕРЕ через executeReadTool();
   - добавить в messages: { role:"assistant", content:<json-ответ модели> },
     { role:"user", content:"[Результат инструмента " + tool + "]:\n" + result };
   - вернуться к шагу 1 (максимум 5 итераций).
3. Если ответ = {"type":"answer"} или {"type":"write"} — вернуть клиенту как сейчас
   (write по-прежнему подтверждается кнопкой «Выполнить» в приложении).
4. Превышен лимит итераций → вернуть последний read_result как answer.
```

Правки в SYSTEM_PROMPT:

```
Ты можешь вызывать инструменты чтения НЕСКОЛЬКО раз подряд для одной команды —
используй это для сложных вопросов («найди товар, потом покажи кто его купил»).
После получения результата инструмента ты увидишь его в сообщении [Результат инструмента …]:
анализируй числа, сравнивай, делай выводы и отвечай администратору обычным текстом (type:"answer").
Не пересказывай сырые данные без анализа, если вопрос аналитический.
```

Клиент приложения менять НЕ нужно: формат ответа `/api/admin/agent/chat` остаётся прежним
(`read_result` теперь приходит уже «переваренным» ответом типа `answer`).

## Задача 2: даты у `get_abandoned_carts`

**Файл:** `server/admin-tools.ts`, функция `getAbandonedCarts`.

Новые params: `{ dateFrom?: string (ISO), dateTo?: string (ISO), sort?: "newest"|"oldest" (default "newest"), limit? }`.

Логика:
1. Собрать пары (sid, ts), отбросить сессии без даты.
2. Фильтр по dateFrom/dateTo (по ts).
3. Отсортировать по ts (newest = свежие сверху).
4. limit применять ПОСЛЕ сортировки/фильтра.
5. В заголовке указывать выбранный период, если задан.

Обновить строку в SYSTEM_PROMPT:

```
- get_abandoned_carts — брошенные корзины. params: { limit?, dateFrom?, dateTo?, sort?: "newest"|"oldest" }. Поддерживает периоды: «за вчера» → dateFrom/dateTo = начало/конец вчерашнего дня; «за неделю», «за сегодня» и т.д. По умолчанию сортировка от самых свежих.
```

## Задача 3: явные периоды у `get_revenue_by_period` и `export_orders_csv`

**Файл:** `server/admin-tools.ts`.

- `get_revenue_by_period`: добавить `dateFrom?`/`dateTo?` (ISO). Если заданы — использовать их
  вместо относительного `days`. В заголовке ответа писать человеческий период.
- `export_orders_csv`: то же самое — `dateFrom?`/`dateTo?` поверх `days`.

Обновить описания в SYSTEM_PROMPT соответственно.

## Задача 4: таймзона Europe/Moscow

**Файл:** `server/admin-tools.ts`.

Группировка дней в `getRevenueByPeriod` использует `toISOString()` (UTC) — вечерние заказы по Москве
попадают в предыдущий день. Заменить на сдвиг +3 часа:

```ts
const MSK_OFFSET = 3 * 3600000;
const dayKey = (iso: string) => new Date(new Date(iso).getTime() + MSK_OFFSET).toISOString().slice(0, 10);
```

Применить тот же сдвиг во всех местах, где режем по дням (analyze_orders, export_orders_csv,
границы dateFrom/dateTo для «вчера»/«сегодня»).

## Задача 5: текущая дата в SYSTEM_PROMPT

Модель не знает сегодняшнюю дату, поэтому «вчера», «на этой неделе» она не может перевести в ISO.
В `processAdminCommand` перед системный промт подставлять актуальное время:

```ts
const nowLine = `Сегодня: ${new Date().toLocaleString("ru-RU", { timeZone: "Europe/Moscow", dateStyle: "full", timeStyle: "short" })} (МСК). Относительные периоды («вчера», «за неделю», «в этом месяце») переводи в ISO-даты от этой даты.`;
const messages = [
  { role: "system", content: SYSTEM_PROMPT + "\n\n" + nowLine },
  ...
];
```

## Шаги проверки (после деплоя)

В чате BOOOM AI (приложение AdminBMG или веб-админка):

1. «Покажи брошенные корзины за вчера» → только корзины вчерашнего дня, отсортированы от свежих.
2. «Выручка с 1 по 15 августа по дням» → таблица именно за эти даты, московские дни.
3. «Найди худи oversize и скажи кто их покупал» → агент делает 2 вызова подряд и сводит ответ.
4. Регресс: «сколько продалось мерч людмил огурченко», «создай промокод TEST20 на 20%» — старые сценарии работают.

## Что НЕ входит

Приложение AdminBMG менять не нужно — оно уже готово: локальная аналитика оставлена только
как фолбэк при недоступности сервера, все вопросы уходят агенту.
